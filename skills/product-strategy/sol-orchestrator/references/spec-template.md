# Technical specification template

Use every section; write `None — <reason>` when it does not apply.

```markdown
# SPEC: <Feature>

## 1. Problem and user-visible outcome
## 2. Goals and binary acceptance criteria
## 3. Non-goals
## 4. Assumptions and unresolved questions
## 5. Constraints and permission boundaries
## 6. Existing architecture and reusable components
## 7. Chosen architecture and rejected alternatives
## 8. Component ownership and responsibilities
## 9. State transitions and data flow, including failure paths
## 10. API and public contract changes
## 11. Data, schema, migration, backfill, and rollback
## 12. UI states, responsive behavior, and accessibility
## 13. File-level modifications
## 14. Edge cases and error handling
## 15. Security and privacy
## 16. Performance and observability
## 17. Testing and validation strategy
## 18. Rollout, monitoring, rollback triggers
## 19. Risks
## 20. Definition of done
```

Name real files and resources. Give extra depth to irreversible, security-sensitive, data-changing, and public-contract work; do not pad low-risk sections.
